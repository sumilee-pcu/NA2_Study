## 기존 문제은행과의 연결

아래는 주제 수준의 대응이다. 블로그가 각 문항의 정답을 새로 인증했다는 의미는 아니며, 기존 PDF 쪽수와 1차 근거는 유지한다.

| 참고할 주제 | 기존 문항 | 활용 판단 |
|---|---|---|
| IPv4 마스크·네트워크 주소 | PRAC-001, 002, 009, 010 | 계산 흐름의 설명 방식 참고. 서로 다른 조건의 예제를 그대로 치환하지 않음 |
| ARP·DHCP | PRAC-004, 006 | 기능을 구별하는 짧은 답안 연습과 연결 가능 |
| TCP·OSPF | PRAC-011, 014, 023 | 기존 개념 문항과 연결. TCP 헤더 설명은 아래 교정 필요 |
| 사설 IPv4·SNMP 포트 | PRAC-018, 019 | 기존 주소 블록·서비스 구별 문항의 복습 주제로 활용 |
| 케이블링·Windows Server·라우터 | 이번 24문항과 별도 | 작업형·실습형 콘텐츠 후보로 관리 |

나머지 기존 문항은 이 자료로 교차 검증했다고 표시하지 않는다. Linux 명령·파일·권한 문항 등은 기존에 검수한 근거를 그대로 사용한다.

## 우선 교정·보류할 5개 항목

| 항목·원문 위치 | 확인된 문제 | 1차 근거에 따른 교정과 적용 |
|---|---|---|
| 시간 환산 · Windows Server 부분 | 1분을 600초, 1시간을 36000초로 적음 | **1분 = 60초, 1시간 = 3600초**이다. 설정값 문제에 옮기기 전에 단위와 숫자를 다시 계산한다. [NIST SP 330 §4, Table 8](https://www.nist.gov/pml/special-publication-330/sp-330-section-4) |
| ARP/RARP 계층 · 앞쪽 두 표 | RARP 분류가 표마다 달라짐 | RFC 903은 RARP를 데이터링크 수준 프로토콜로 명시하고 RFC 1122는 ARP를 링크 계층 장에서 다룬다. 단일 OSI 계층 답안을 출제할 때에는 적용 모델을 명시한다. 이번 PRAC-004처럼 주소 해석 기능을 묻는 문항은 유지한다. [RFC 903, Proposed Protocol](https://www.rfc-editor.org/rfc/rfc903.html), [RFC 1122 §2.3.2](https://www.rfc-editor.org/rfc/rfc1122.html#section-2.3.2) |
| NDP·DAD·Ping · ICMPv6 부분 | 이웃 검색과 Ping을 묶고 DAD를 도달성 확인으로 설명 | 이웃 주소 해석·도달성 추적, 주소 중복 검사, Echo 진단을 구분한다. **DAD는 링크에서 주소의 중복 여부를 검사**하며, 이웃 도달성 추적은 NUD이다. IPv6 Echo Request/Reply는 별도 ICMPv6 메시지로 정의된다. [RFC 4861 §7.3](https://www.rfc-editor.org/rfc/rfc4861.html#section-7.3), [RFC 4862 §5.4](https://www.rfc-editor.org/rfc/rfc4862.html#section-5.4), [RFC 4443 §4](https://www.rfc-editor.org/rfc/rfc4443.html#section-4) |
| TCP 헤더 · 필드 표 | 예약 6비트와 플래그 9비트를 함께 제시하고 옵션을 16비트 단위로 설명 | **RFC 9293 §3.1의 기준 그림**은 예약 4비트와 제어 비트 8개를 표시한다. 개별 옵션 길이는 8비트 배수이고 패딩을 포함한 헤더 전체 길이는 32비트 배수이다. 확장에 따른 배치를 섞지 말고 문항에 적용 RFC·확장을 명시한다. 이 검토는 이후 모든 확장의 비트 수가 같다는 주장이 아니다. [RFC 9293 §3.1](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.1) |
| `no shutdown` · 라우터 후반 | 반복 입력 시 토글된다는 에뮬레이터 경험담 | Cisco IOS 문서는 `shutdown`을 비활성화, `no shutdown`을 비활성화 해제로 정의한다. 일반 명령 의미를 토글로 설계하지 않는다. 2026-10-23 ICQA 라우터 시험 데모(router.exe 1.0.0.0)에서는 같은 인터페이스에 두 번째 `no shutdown`을 입력하면 메시지 없이 `administratively down`과 `shutdown` 행이 생기고, 세 번째 입력에서 다시 up이 되는 동작을 **두 차례 재현**했다. 실습 자료에는 데모의 특이 동작으로 한 번만 입력하도록 안내하며, IOS 명령 의미로 일반화하지 않는다. 재현 기록은 [실습 검수 보고서](PRACTICAL_LABS_VERIFICATION.md#icqa-에뮬레이터-직접-검증)에 있다. 문제에 없는 명령을 자체 채점의 필수 조건으로 추가하지 않는다. [Cisco IOS: shutdown (interface)](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/interface/command/ir-cr-book/ir-s6.html) |

위 표의 원문 관찰은 상단 링크의 해당 구간을 기준으로 하고, 교정 내용은 각 행의 1차 자료를 기준으로 한다. 다섯 항목 이외의 모든 문장을 옳다고 판정한 것은 아니다.

## 후속 콘텐츠 후보와 검수 조건

| 영역 | 후속 후보 | 반영 전 확인할 일 |
|---|---|---|
| 단답형/객관식 | 듀얼 스택, NAT/NAPT, Linux 리다이렉션·예약 작업, Windows ping | 운영체제·버전·조건을 명시하고 허용 답안·오답 보기를 별도로 검수. NAT와 주소·포트 변환의 범위는 [RFC 3022 §2](https://www.rfc-editor.org/rfc/rfc3022.html#section-2)부터 확인 |
| Windows Server 실습 | 서비스·웹/FTP·보안 설정 | 실제 문제 화면의 단위·속성·버전을 대조하고 현재 공식 에뮬레이터에서 재현 |
| 독립 라우터 실습 | DHCP 풀·보조 IP·캡슐화·VTY/SSH·OSPF | 전체 초기 설정과 지원 명령을 확인하고 정답·오답·저장 결과를 재현. 본문의 사례만으로 2급 출제 범위를 확정하지 않음 |
| 작업형 | 결선과 제작 순서 | 기존 T568A/B·관찰 방향·실물 점검 기준과 비교 |

이 후보들은 범위 탐색 결과이며 새 문항으로 승인하거나 앱에 추가한 상태가 아니다. 게시글의 입실 시간·준비물·문항 번호·빈도·난이도 평가는 해당 회차의 공식 안내와 구분하여 다룬다.
